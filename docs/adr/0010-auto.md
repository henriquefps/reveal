# ADR 0010: Auto

Status: accepted (M1, Auto). Date: 2026-11-11. Builds on ADR 0007 (Light operators) and ADR 0008 (profiles, Auto
white balance). The seed of M3's smart presets (`docs/plan/architecture.md`, "Analysis and smart presets").

One tap on **Auto** (the tool strip) sets exposure, contrast, highlights, shadows, whites, blacks and vibrance, and
the white balance when its mode is **Auto WB**. The Light panel's **Auto** sets the Light group only. The result is
plain slider values, written as **one history step** (`HistoryAction.AUTO`, ADR 0003), so it can be changed, undone or
copied like any other edit (product principle 4: "help, don't take over"). Code: `:core:pipeline` `auto/AutoAnalysis.kt`
(analysis) and `auto/AutoRules.kt` (rules, parameters, apply); editor wiring in `EditorViewModel.auto`.

## Shape: `analysis -> partial Recipe`

```
sample  = AutoAnalyser.sample(proxy)                 // at open, 512 px, point-sampled (kept, ~2 MB)
wb      = (mode == AUTO) ? AutoRules.whiteBalance(WbAnalysis) : recipe's   // ADR 0008, snapped to slider steps
a       = AutoAnalyser.analyse(sample, recipe with wb, Light and colour sliders neutral)
result  = AutoRules.compute(a, AutoParams())         // pure: numbers in, slider values out
recipe' = AutoRules.applyTo(recipe, result, scope)   // ALL or LIGHT
```

- **Pure and deterministic.** `AutoAnalysis` is plain numbers (histograms, a tone table, two scalars); the rules are
  pure Kotlin on it with every constant in `AutoParams` (M3's smart presets expose some of them: "target subject
  brightness" = `targetGrey`, "max shadow lift" = `maxShadows`). JVM-tested on fixtures of analysis values
  (`AutoRulesTest`).
- **Idempotent.** The analysis renders the sample with the recipe's profile, white balance and crop but with every
  Light and colour slider at "no change", so Auto's own values never feed back: tapping twice gives the same recipe
  (tested on the JVM and on the device; the second tap adds no history step). Auto WB is a function of the input only.
- **On top of the profile.** The tone table is the current profile at its amount, so Auto on Neutral/Flat or Camera
  JPEG match aims at the same display brightness through that look's own curve; the profile is never changed.
- **CPU, not a GPU readback.** The task suggested a readback of a small mip. The analysis instead runs the CPU
  reference (ADR 0002) on a 512 px point-sampled copy of the proxy kept from the open: bit-identical on every device
  (a GPU readback differs between drivers and fp16 render targets, which would break "deterministic"), JVM-testable,
  and independent of the renderer's state (crop mode, compare, clipping overlays). Cost on the emulator (Apple M4 Pro
  host): **80-240 ms** per tap including the analysis (`adb logcat -s RevealEditor`, `auto ...`), off the main
  thread; re-measure on the phone. Point sampling (not area averaging) keeps clipped pixels clipped, so highlight
  reconstruction and the clipped fraction see real pixels.

## The analysis (`AutoAnalysis`)

Tone axis `s = log2(Y)`, `Y` the Rec.2020 luminance of the scene-linear sample at exposure 0, after white balance,
highlight reconstruction and the camera matrix (the axis of ADR 0007's local tone base: 0 = reference white, -2.47 mid
grey). 16 bins per stop over -16..+6.

| Field | What |
| --- | --- |
| `histogram` | fraction of pixels per bin (inside the crop) |
| `centreHistogram` | the same, weighted `1 + 2 exp(-r² / (2 · 0.2²))` (`r` from the centre in frame units): the subject is more often near the centre |
| `toneTable` | display `Y` of a neutral of luminance `2^s` through the profile (identity for display-referred input) |
| `clippedFraction` | pixels with a raw channel at 99 % of the sensor clip |
| `medianChroma` | median OkLab chroma of the display-referred render over mid-tones (display `Y` 0.05-0.8) |
| `sceneReferred` | false for JPEG/HEIF (their whites are not recoverable) |

`percentile`, `trimmedMean`, `display(s)` (the table, linear in between, a linear toe below), `sceneFor(y)` (its
inverse, bisection) and `displayHistogram()` (lightness, 64 bins: the display-referred histogram) are methods.

**Faces are deferred to M3/M4** (approved by the orchestrator). ML Kit's bundled face detection (what Hoard's ADR 0009
uses) is distributed under Google's proprietary ML Kit terms, a poor fit for this AGPL-3.0-or-later repository, and
adds several MB to the APK; M4's ML spike (subject/people segmentation with an open licence, `architecture.md`, "On-device
ML") gives a subject mask, and M3's smart presets then weight the key by subject/face brightness. Until then the
centre-weighted histogram stands in for the subject.

## The rules (`AutoRules`)

Each rule predicts its effect with the operators' own transfer functions on a few percentiles: the local tone curve
`LocalToneOp.delta` (ADR 0007) on the scene stop, the profile's tone table, the global tone curve `GlobalToneOp.curve`
on lightness `cbrt(Y)`. In pipeline order:

1. **Exposure.** Key = centre-weighted median of `s` (`keyMedianWeight` 1, `keyCentreWeight` 1). EV puts the key on
   display `Y` = `targetGrey` 0.17: `EV = sceneFor(0.17) - key`. Highlight protection: when that leaves the 99.5th
   percentile more than 1.5 stops past the highlight ceiling, EV is lowered, by at most 1 EV (Shadows then carries
   the rest). Limited to ±3 EV, snapped to 0.01 EV.
2. **Highlights** (0..-60): the smallest pull that brings the 99.5th percentile under display `Y` 0.90 (the start of
   the profile's shoulder). Display-referred input: never below where the original had it.
3. **Shadows** (0..+40): the smallest lift that brings the 5th percentile up to display `Y` 0.012.
4. **Contrast** (-15..+20): moves the lightness spread (p75 - p25) 20 % of the way to 0.40.
5. **Whites** (-20..+30): puts the 99.5th percentile on lightness 0.98 (after contrast).
6. **Blacks** (-20..+10): puts the 0.5th percentile on lightness 0.12.
7. **Vibrance** (0..+20): `400 · (0.11 - medianChroma)`, never negative.

Slider values are whole units (exposure 0.01 EV); integer searches break ties towards 0 (the gentler edit). The white
balance (Auto WB mode only) is ADR 0008's estimate, snapped to the temperature slider's 10 K step and whole tint; the
Auto WB chip uses the same function (`AutoRules.whiteBalance`, which replaced the editor's earlier grey-world chip
value), so the chip and the tool always agree.

## Calibration

**Data:** copies of the owner's 31 ZV-E10 RAW+JPEG pairs from two shooting days (17 + 14), the same set as ADR 0008's
calibration; copied to a work directory outside the repository, decoded with `scripts/calibration/rawdump.sh`, deleted
after the run. Only aggregates are reported here.

**Method** (`AutoCalibrationTest`, opt-in, `REVEAL_CALIBRATION_DIR` as for ADR 0008; `REVEAL_AUTO_FIT=1` adds the
fit): Auto (Standard, as-shot WB) on each RAW at about 640 px, rendered by the CPU reference, against the camera
JPEG at the same size: CIE L\* at the 5/25/50/75/95th luminance percentiles and the median OkLab chroma of mid-tones.
Two fits by coordinate descent: (1) the exposure constants on the median L\* alone, (2) the tone constants on the
*shape* (each percentile's error minus the pair's median error) plus chroma, so tone sliders cannot hide exposure
errors.

**Findings.**

- The camera's own exposure and Standard already agree: the as-opened render is within 0.36 L\* of the camera at the
  median (Standard was fitted to it in ADR 0008). The question for Auto is how well a scene-independent rule recovers
  the camera's brightness, and what it does to badly exposed files.
- Exposure: the fit chose the **centre-weighted median** as the key (pure median over the median/log-average mixes,
  full centre weight over none) and `targetGrey` 0.16. The two days are biased in opposite directions (Auto -2.7 L\*
  on the indoor day, +3.3 on the other): the camera's metering keeps context the histogram alone does not
  (a baby's face indoors, a bright outdoor scene). Faces/subject (M3/M4) are the expected fix.
- Tone: with free constants the shape fit runs to the ends of every range (highlights -80 and blacks -30 on almost
  every photo, contrast +30 with blacks +10 in another run): it uses the sliders to imitate the camera's DRO and
  saturation, a degenerate trade-off between sliders rather than a better rule. The shipped tone constants are
  therefore **designed** (the values listed above, inside the ranges the fit explored) and measured, not fitted.
- **Taste:** the owner likes "bright, natural": `targetGrey` = fitted 0.16 x 1.07 = **0.17** (about +1 L\* at the
  median); vibrance at most +20; highlights at most -60.

**Results** (ΔL\* = Auto minus the camera JPEG, mean / mean of |.|; 31 pairs):

| Render | p05 | p25 | p50 | p75 | p95 | Chroma | \|ΔL\* p50\| median / max |
| --- | --- | --- | --- | --- | --- | --- | --- |
| as opened (no Auto) | +0.48 / 0.55 | +0.43 / 0.44 | +0.30 / 0.36 | -0.18 / 0.36 | -1.18 / 1.23 | -0.0038 | 0.32 / 0.88 |
| Auto, first constants (before calibration) | +0.65 / 3.52 | +6.89 / 7.71 | +9.08 / 9.77 | +7.45 / 8.73 | +0.14 / 5.64 | +0.0031 | 9.61 / 21.32 |
| Auto, fitted exposure, free tone fit | -3.13 / 3.40 | -2.08 / 3.86 | -1.01 / 4.48 | -1.79 / 6.22 | -3.31 / 6.47 | +0.0006 | 3.84 / 12.14 |
| **Auto, shipped** | -0.96 / 2.53 | +1.33 / 4.33 | +2.69 / 5.86 | +2.12 / 7.41 | -0.76 / 5.62 | +0.0010 | 4.75 / 13.35 |
| RAW 1.5 EV under-exposed, as opened | -6.27 / 6.27 | -13.86 / 13.86 | -19.53 / 19.53 | -25.08 / 25.08 | -27.35 / 27.35 | -0.0121 | 19.59 / 24.46 |

A 1 L\* step is just noticeable side by side; around mid grey 1 EV is about 15-20 L\*, so the shipped median error is
about 0.3 EV, slightly bright by design. Shipped slider values on the 31 pairs: exposure -1.28..+0.99 EV (median -0.06),
contrast -15..+20 (median +20), highlights -60..0 (median -60), shadows 0..+40 (median +22), whites -13..+30 (median
-5), blacks -20..+3 (median -16), vibrance +18..+20. Highlights -60 / shadows +22 / contrast +20 is the usual
"recover the window, open the room, restore the mid-tone contrast" pattern of an automatic edit; it is visible and
undoable as plain values.

**Robustness:** Auto is shift-invariant: on the public samples a 1.5 EV darker copy gets exactly +1.50 EV more and the
same tone values (`AutoRulesTest` checks it on fixtures). On the owner's pairs the under-exposed copies land within
5.3 L\* of the camera at the median (19.5 without Auto); the residual difference to the normal run comes from clipped
raw highlights, which are no longer clipped once the copy is scaled down.

## Tests

- `AutoRulesTest` (JVM): exposure lands the key on the target; under-exposure is corrected by the same EV with
  identical tone values; limits; a moderate scene gets small edits; highlights pull more with more headroom and
  protection lowers the exposure by at most 1 EV; blocked shadows lift within the limit; contrast follows the spread;
  vibrance bounds; display-referred whites never pulled; values are slider steps; analysis and rules deterministic;
  Auto twice = Auto once (both scopes, from any slider state); Light scope leaves colour alone, ALL sets vibrance and
  (in Auto WB) the snapped Auto white balance; Auto follows the profile; the analysis only sees the crop; the sample
  keeps clipped pixels.
- `EditorAutoTest` (instrumented, CC0 ZV-E10 RAW and a synthetic JPEG): tap Auto -> Light values set, profile kept;
  second tap identical; one undo returns to the original and redo restores it; the Light panel's Auto after a panel
  reset restores the same Light values and leaves colour alone.
